# Migrating Existing Servers to MCP `2026-07-28`

Read this when upgrading a 2025-era server or adding dual-era support. The
modern revision is a new protocol era, not a feature flag layered onto an
initialized session.

## 1. Choose the compatibility target

Inventory every real client and record its product version and test date. Then
choose one of these targets:

| Target             | Use when                                    | Required shape                                                   |
| ------------------ | ------------------------------------------- | ---------------------------------------------------------------- |
| Modern only        | Every required client supports `2026-07-28` | Reject legacy openings and keep the endpoint fully stateless     |
| Dual era           | Required clients span 2025 and 2026         | Use an SDK entry that isolates each era's complete wire behavior |
| Legacy maintenance | Required clients are still 2025-only        | Keep the legacy target explicit and plan a modern migration      |

A product announcement that support is “rolling out” does not prove that every
web, desktop, CLI, connector, or embedded surface has shipped it. Probe and test
the exact host rather than guessing from vendor-level support.

## 2. Replace lifecycle assumptions

For the modern path:

- remove `initialize` and `notifications/initialized`
- stop minting, storing, routing, or echoing `Mcp-Session-Id`
- process protocol version, client identity, and client capabilities from each
  request's `_meta`
- implement and test `server/discover`
- return server identity in result `_meta`
- make request handlers safe to run on any instance behind a round-robin load
  balancer

Do not replace a protocol session with a hidden cookie or connection-local map.
If application state spans calls, mint an explicit opaque handle and pass it
through normal results and arguments. Authorize the handle on every use.

List results may vary by verified authorization context, request parameters,
or deployed configuration, but not by an implicit connection identity.

## 3. Implement dual-era serving deliberately

A dual-era server selects one coherent behavior family from the client's
opening:

- a request carrying the modern per-request metadata envelope selects modern
  stateless semantics
- legacy `initialize` selects the negotiated 2025 behavior for that connection
  or legacy HTTP session

The official TypeScript v2 `createMcpHandler(factory)` serves modern requests
and stateless 2025-era HTTP requests from one endpoint by default. Use
`legacy: "reject"` for modern-only serving. A sessionful v1 deployment needs an
explicit legacy handler in front of a strict modern handler; do not recreate
session storage inside the modern factory. `serveStdio(factory)` performs the
equivalent era selection for stdio.

For custom clients, a well-formed modern response can identify a modern server
even when it reports an error. Correct the request or select a mutually
supported version; do not treat every HTTP `400` as permission to fall back.
Cache the selected era for the server process or HTTP origin and re-probe when
that assumption fails.

The official `@modelcontextprotocol/client@2.0.0` automatic classifier is more
conservative: a valid `server/discover` result or well-formed `-32022` response
is modern evidence, while `-32020` and `-32021` can still fall back to legacy.
The client also defaults to legacy unless `versionNegotiation` is explicit. Pin
`2026-07-28` and add raw-wire tests for the modern path; test automatic fallback
separately rather than treating it as conformance proof.

Test both paths independently. A shared application handler does not prove that
both wire protocols are correct.

## 4. Move server-to-client requests to MRTR

Replace direct `elicitation/create`, `sampling/createMessage`, and `roots/list`
requests with Multi Round-Trip Requests for the supported originating methods:

- `tools/call`
- `resources/read`
- `prompts/get`

Return `resultType: "input_required"` with `inputRequests` supported by the
caller's declared capabilities. The client resolves them and retries the same
method with a new JSON-RPC ID, `inputResponses`, and the exact `requestState`.

Treat every retry as an independent request:

- encode the workflow phase and required context in integrity-protected
  `requestState` or durable server storage
- bind protected state to the principal, operation/arguments, and a short
  expiry
- enforce server-side single use when replay could duplicate a sensitive action
- never assume the client will answer or retry
- avoid performing irreversible work before requesting confirmation; otherwise
  make the step resumable and idempotent

`inputResponses` contains only the current round. Carry earlier answers forward
inside protected state when a workflow has multiple input rounds.

## 5. Replace transport streams and subscription behavior

Modern Streamable HTTP is POST-only at the MCP endpoint:

- return JSON or a request-scoped SSE response
- return `202` with no body for an accepted notification
- return `405` for legacy GET/DELETE on a modern-only endpoint
- ignore, but never mint or depend on, legacy `Mcp-Session-Id` and
  `Last-Event-ID` headers
- cancel an HTTP request when its SSE response stream closes; do not POST
  `notifications/cancelled` on the modern HTTP path

Replace the standalone GET event stream and
`resources/subscribe`/`resources/unsubscribe` with `subscriptions/listen`.
Keep progress and opted-in logging notifications on the originating request's
response stream, not the subscription stream.

Do not assume omitting a subscription capability disables listen. The official
TypeScript v2 handler installs its listen router independently. Either reject
listen explicitly and prove it never opens SSE, or configure a real shared
event bus, bounded capacity, cancellation, fan-out, and reconnect behavior.

SSE resumability is gone. If a response stream breaks, the client reissues the
operation with a new request ID. A mutating tool may therefore finish even when
the client never receives its result. Use domain idempotency keys, conditional
writes, operation handles, or status/read-after-write tools where duplicates
would be harmful. Set `idempotentHint` only when repeat execution is actually
safe.

## 6. Add header routing without trusting it blindly

Every modern JSON-RPC request POST carries `MCP-Protocol-Version` and
`Mcp-Method`, plus `Mcp-Name` where the method has a name or URI. Gateways can
route, authorize, meter, and rate-limit without parsing JSON bodies. The
`2026-07-28` revision does not define these header requirements for notification
POSTs; do not silently impose the request rules on them.

The component that processes the body must decode mirrored values and verify
that headers match the body. Missing, malformed, or mismatched required headers
return HTTP `400` with `HeaderMismatch` (`-32020`). Never trust a mirrored
header from an older or unvalidated request.

Use `x-mcp-header` only for primitive tool arguments that an intermediary
genuinely needs. Never mirror secrets, credentials, payment data, or PII.
Schema changes can make a client's cached mirrored-header plan stale; clients
should refresh `tools/list` after a header mismatch.

## 7. Make discovery and reads intentionally cacheable

Add `ttlMs` and `cacheScope` to complete results from:

- `server/discover`
- `tools/list`
- `prompts/list`
- `resources/list`
- `resources/templates/list`
- `resources/read`

Use `private` whenever the result varies by user, tenant, access token, or
scope. `public` permits reuse across authorization contexts even on an
authenticated endpoint. Keep tool ordering deterministic. Keep the same cache
scope across every page of a paginated list.

TTL is a freshness hint checked when data is needed, not a polling interval or
a promise that the underlying data cannot change. Relevant subscription
notifications invalidate cached results immediately. Never cache MRTR retries
that contain `inputResponses` or `requestState`.

## 8. Harden authorization

For protected HTTP servers:

- preserve OAuth Protected Resource Metadata and RFC 8707 resource/audience
  binding
- record the authorization-server issuer before redirect and validate a
  returned RFC 9207 `iss` by exact comparison before code redemption
- bind stored client credentials to that issuer and re-register after an issuer
  change
- require the appropriate OIDC `application_type` when retaining deprecated DCR
- prefer pre-registration or Client ID Metadata Documents over DCR
- keep MCP endpoint credentials separate from credentials used for upstream
  services

These changes affect OAuth clients and authorization servers as well as MCP
resource servers. Test the complete login, refresh, scope step-up, issuer-change,
revoke, and reauthorization flow with each host.

## 9. Update schemas, results, and errors

- Emit `resultType: "complete"` on ordinary core results. Core MRTR interim
  results use `"input_required"`; negotiated extensions may define additional
  values, such as Tasks' `"task"`.
- Accept the full JSON Schema 2020-12 vocabulary for tool input/output schemas
  and any JSON value in `structuredContent`.
- Do not automatically fetch network `$ref` targets. Bound recursive and
  composition-heavy schema evaluation.
- Return resource-not-found as `-32602`; accept legacy `-32002` only when
  consuming older servers.
- Reserve `-32020` through `-32099` for specification-defined errors. New codes
  MUST NOT be allocated in the legacy `-32000` through `-32019` MCP subrange,
  and modern implementations SHOULD NOT emit it. Do not emit historical
  `-32002` or `-32042`. Prefer tool results for expected domain failures; if a
  custom JSON-RPC error is unavoidable, choose outside both MCP-reserved ranges.
- Treat generated JSON Schema `minimum`, `maximum`, and `default` values as
  numbers, not integer-only fields.

## 10. Handle extensions and removed/deprecated features

Extensions are negotiated per request in client capabilities and advertised in
`server/discover`. They evolve independently of the core revision and need a
core fallback.

The modern Tasks extension uses `resultType: "task"`, durable task handles,
polling with `tasks/get`, input through `tasks/update`, and cooperative
`tasks/cancel`. It does not use the old blocking `tasks/result` or `tasks/list`.
Do not return a task unless the client declared the extension.

Remove assumptions about core `ping`, `logging/setLevel`, and
`notifications/roots/list_changed`. Use an ordinary HTTP health endpoint for
load-balancer health, per-request `logLevel` only for the deprecated MCP logging
surface, and application-specific invalidation for configured path state.

New implementations should not adopt Roots, Sampling, Logging, DCR, HTTP+SSE,
or Sampling's `includeContext: "thisServer"` / `"allServers"`. Roots, Sampling,
Logging, and DCR first become eligible for removal in a revision released on or
after `2027-07-28`; actual removal may occur later. Check the live deprecated
features registry rather than treating that date as a guaranteed removal.

## Migration verification matrix

Run these checks for each supported transport, protocol era, and real host:

- discovery/version selection and recognized-modern-error fallback behavior
- required request `_meta`, `resultType`, cache fields, and server identity
- standard/mirrored HTTP headers, Base64 decoding, mismatch rejection, Host,
  and Origin
- every enabled response mode, stream cancellation when SSE is enabled, and
  lost-response retry
- deterministic lists, pagination cache scope, and subscription invalidation
- MRTR capability rejection, multi-round state, tamper/replay protection, and
  abandoned flows
- when OAuth is selected: discovery, audience, PKCE, `iss`, registration,
  issuer changes, refresh, and scope step-up
- schema composition bounds, external `$ref` rejection, structured output, and
  modern error codes
- extension opt-in/fallback and durable Tasks behavior when used
- explicit proof that legacy sessions/GET/replay remain confined to the legacy
  path

Passing tool calls through one SDK client is not enough. Include raw-wire or
conformance tests so SDK-added fields and fallback behavior are visible.
